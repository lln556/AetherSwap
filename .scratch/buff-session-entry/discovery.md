# BUFF 登录状态入口与浏览器会话导入：设计访谈

Status: needs-info
Created: 2026-10-30

## 用户提出的目标

- 在前端提供常驻入口，主动检测服务器保存的 BUFF 会话是否有效。
- 会话失效时，希望借助浏览器插件，从同一 Chrome 浏览器中的 BUFF 登录会话取得 Cookie，减少手工复制。

## 已核实的技术事实

- Chrome 官方 Cookies API 要求扩展声明 cookies 权限及相应网站权限，可读取包含 HttpOnly 标记的 Cookie。普通网页脚本不能用此扩展 API。
- 扩展与网页可通过消息机制通信，需限制允许通信的网站。
- 浏览器当前会话与服务器保存的会话是两个不同的验证对象；浏览器登录不能直接证明服务器保存的凭据有效。
- 参考：Chrome for Developers 的 Cookies API 和 Message passing 官方文档（2026-10-30 核对）。

## 待确认的设计分支

- 是否接受安装专用 Chrome 扩展；首版的浏览器/个人资料/无痕支持范围和安装方式。
- 常驻入口的位置、主动检测与自动检测策略、状态定义和检测时间。
- 导入触发方式、扩展授权的目标服务、不同账号或会话切换的处理。
- 服务端验证失败时旧凭据保留规则，以及交易任务运行或待付款期间的处理。
- 保存凭据后是否自动恢复交易；手动粘贴兜底。

以上是访谈记录，不代表已批准架构或开始实现。明确选择后再记录必要 ADR 与领域术语。

## 2026-10-30：免扩展方案待选

用户追问是否可以不安装插件，尚未确认采用扩展。

- 普通 AetherSwap 网页无法直接读取另一个域的标签页 Cookie；书签脚本也无法读取 HttpOnly Cookie，不能承诺完整自动导入。
- 免安装的直接方案：常驻检测按钮 + 手动粘贴入口 + 复制指引。
- 免客户端安装且免手动复制的候选方案：服务器提供专用登录浏览器，并将交互画面送到网页；用户在该会话中登录，服务端从自己管理的浏览器取得 Cookie。它不会继承用户本地 Chrome 的已登录标签页，仍需验证 BUFF 登录与安全验证的实际兼容性。
- 尚待确认用户更重视免安装、免复制，还是复用本地浏览器已有登录；此选择决定后续研究与设计分支。

## 2026-10-30：已确认采用 Chrome 扩展

用户回答“那还是安装插件吧”，确认采用扩展路线。记录为 `docs/adr/0001-buff-session-import-browser-extension.md`；不再将免扩展远程登录作为首版设计分支。

下一轮待确认：首版安装分发方式；常驻入口与检测触发；用户主动导入及目标服务绑定；运行中/待付款时禁止替换和保存后不自动启动交易。此前建议不视为用户已经同意这些细节。

## 已确认：第一轮四项决定

用户回复“同意”，确认：

1. 首版提供扩展文件包与手动安装说明，暂不上架 Chrome 网上应用店。
2. 首页 BUFF 状态卡片常驻“检测登录”“从浏览器导入”“手动填写”，显示最近检测时间；点击才做在线检测，页面刷新只读取已有检测结果。
3. 首版支持同一个 Chrome 个人资料中的普通窗口，用户主动点击并确认目标服务后才读取、传送 Cookie；不后台自动同步。服务端验证成功才替换旧凭据，失败保留旧凭据。
4. 买入运行、待付款或有未核实订单时禁止替换凭据；更新成功不自动启动买入。现有自动重新启动逻辑需要调整。

## 第二轮待确认

- 扩展按具体服务来源（协议、主机、端口）授权；新增地址重新授权，导入逐次显示目标。
- 导入会话绑定的 Steam 账号必须与 AetherSwap 当前账号匹配；不匹配或无法核实则拒绝替换，不替用户切换账号。
- 区分过期、需要验证、限流与网络失败；扩展导出成功不等于服务端验证成功。已有风险保护下的恢复方式需要明确允许受控只读验证的边界。

## 已确认：第二轮三项决定

用户回复“都同意”，确认：

5. 扩展只向明确授权的 AetherSwap 来源导入；协议、主机或端口变化需重新授权，每次导入显示目标地址。
6. BUFF 会话绑定的 Steam 账号必须与 AetherSwap 当前选中账号匹配；不匹配或无法核实均拒绝替换，不自动切换账号。
7. 本地完成安全验证后，允许用户主动发起一次受控只读恢复检测；服务器确认证据有效后才恢复会话可用状态。限流冷却期间不重试，不凭 Cookie 已取得或用户声明完成验证就清除限制。明确区分过期、验证、冷却与网络异常，任何情况下都不自动启动买入。
