# 策略预演与行情分析：第一版

Status: ready-for-human
Progress: implemented-and-verified
Created: 2026-10-28
Baseline: 25b9bfb

## Problem Statement

使用者 fork 了 AetherSwap，对继承的策略模块和行情分析功能尚不熟悉。他需要理解程序为何买入、跳过、上架或等待，并判断修改参数会产生什么变化。

现有“模拟”使用固定示例数据，内置筛选模块通常直接返回通过，不能用来确认真实规则是否通过，也不能可靠比较参数。真实交易流程已有规则和日志，但扫描结果没有保存足以重现每次判断的完整依据。事后重新查询行情，也不能解释已经过去的那次检查。

使用者需要一个可以理解、可以核对、不会提交真实交易的策略预演功能。它应明确区分真实检查结果、修改参数后的假设判断、缺少数据，以及尚未执行的检查。

## Solution

第一版围绕真实检查记录提供决策解释和策略预演。

程序保存逐件检查时使用的数据、有效策略参数、评估时刻和结果。使用者在策略中心找到某次检查，查看通俗解释、实际值与阈值，以及相关价格和成交量走势。买入和普通上架支持临时修改参数，并在同一份数据上比较原参数和新参数；自动调价提供原因解释，不支持试改调价专属设置。

比较期间不自动更新行情。缺少后续检查数据时，明确显示无法判断；使用者主动刷新后创建新数据版本，用新版本同时计算两套参数，保留原检查记录。满意的参数只能另存为未启用的策略副本，再通过现有策略中心单独启用。

真实检查记录取代旧示例模拟入口。记录保留最近 7 天、最多 10,000 条，时间或数量限制任一达到时清理最旧记录。新增功能不提交订单、付款、报价、撤单、上架、确认或调价任务。

## User Stories

1. 作为不了解原项目规则的使用者，我希望从真实检查记录进入功能，以便解释程序实际做出的判断。
2. 作为使用者，我希望按买入、普通上架和自动调价筛选记录，以便找到对应业务阶段。
3. 作为使用者，我希望按商品名称和检查结果筛选记录，以便定位某件物品的问题。
4. 作为使用者，我希望看到检查时间、商品、所用策略和结果摘要，以便识别我要查看的那次检查。
5. 作为使用者，我希望列表分页显示，以便记录较多时仍能浏览。
6. 作为使用者，我希望没有真实检查记录时看到明确空状态，以免把演示数据误认为实际结果。
7. 作为使用者，我希望看到检查当时的有效参数，以便不受后来修改正式策略的影响。
8. 作为使用者，我希望看到每项已执行检查的实际值、阈值和原因，以便理解通过、拒绝或等待的依据。
9. 作为使用者，我希望首先看到阻断流程的步骤，以便快速理解程序为何没有继续。
10. 作为使用者，我希望区分未执行、未启用、数据不可用和规则拒绝，以免把缺少证据误认为检查通过。
11. 作为使用者，我希望知道哪些商品并未进入逐件检查，以免把没有记录误认为程序认可或拒绝了它们。
12. 作为使用者，我希望看到行情来源、采集时间、币种和分析窗口，以便知道结论对应什么数据。
13. 作为使用者，我希望看到相关价格与成交量的简单走势图，以便理解波动或活跃程度对判断的影响。
14. 作为使用者，我希望图表和规则结果使用同一数据版本，以便两者能够相互核对。
15. 作为使用者，我希望缺失的历史数据不被补造，以便正确理解图表与结果的局限。
16. 作为使用者，我希望对买入检查临时修改参数，以便理解成本率等限制的影响。
17. 作为使用者，我希望对普通上架检查临时修改参数，以便理解建议定价和暂缓出售的原因。
18. 作为使用者，我希望原参数和新参数并列展示，以便准确知道改了什么。
19. 作为使用者，我希望连续修改参数时行情保持不变，以便把结果变化归因于参数变化。
20. 作为使用者，我希望比较结果突出发生变化的步骤，以便理解哪些规则受到了影响。
21. 作为使用者，我希望某项通过后仍继续遵守后续规则，以免把单项通过误认为整个策略通过。
22. 作为使用者，我希望后续检查缺数据时显示无法判断，以免把未执行的检查当成通过。
23. 作为使用者，我希望主动获取完整行情，以便对原检查尚未取得数据的后续步骤继续研究。
24. 作为使用者，我希望刷新后原参数和新参数都使用新数据重算，以便比较仍然公平。
25. 作为使用者，我希望刷新不会覆盖原检查记录，以便同时区分当时的判断和现在的判断。
26. 作为使用者，我希望刷新失败时保留原结果并显示原因，以便不丢失已经理解的依据。
27. 作为使用者，我希望重复点击刷新不会启动同一记录的多个并发请求，以免无意增加平台请求量。
28. 作为使用者，我希望了解自动调价的挂售时间、价差和原始成本底线，以便理解为什么降价或保持原价。
29. 作为使用者，我希望分清自动调价的策略判断和实际执行结果，以免把建议降价误认为已经撤单重挂。
30. 作为使用者，我希望临时试改不影响正在运行的任务，以便放心比较参数。
31. 作为使用者，我希望满意的参数可另存为未启用的副本，以便保留原策略并稍后决定是否启用。
32. 作为使用者，我希望离开预演而未保存的改动不会改变正式策略，以免意外影响交易。
33. 作为使用者，我希望“检查通过”不被表述为已交易或保证成交，以便正确理解预演结果。
34. 作为使用者，我希望重启程序后仍能查看保留期内的检查记录，以便连续追踪近期问题。
35. 作为使用者，我希望过期或超量记录自动清理，以便避免检查数据无限累积。
36. 作为使用者，我希望检查记录清理不影响购买、成交和交易流水，以便业务历史得到保留。
37. 作为使用者，我希望历史日志缺少的数据不被伪装成完整记录，以便信任新增功能。
38. 作为使用者，我希望保存检查记录失败不会改变正式交易的规则判断，并能看见记录不可用的提示。
39. 作为多账号使用者，我希望记录和刷新对应正确的账号，以免用另一个账号的上下文解释原判断。
40. 作为使用者，我希望记录不包含登录凭据、令牌密钥或支付链接，以便排查判断不需要暴露这些信息。
41. 作为手机使用者，我希望能完成筛选、阅读解释和比较参数，以便无需回到桌面端才能使用。
42. 作为已有策略的使用者，我希望升级后保留现有策略，只替换示例模拟入口，以便继续使用既有配置。

## Implementation Decisions

### 共用判断与执行边界

- 买入和普通上架的正式流程与策略预演共用规则计算，保留现有算法、检查顺序和提前停止行为，不另写一套近似模拟规则。
- 规则计算显式接收业务数据、有效参数和评估时刻。历史窗口、挂售时间、预算及库存等判断所需上下文，以记录中的依据为准；固定数据预演不得偷偷读取当前行情或当前时间替换它们。
- 支持内置模块和现有安全声明式模块。缺少输入或不支持的情况必须明确返回，不能默认通过。
- 第一版只修改既有模块参数，不在预演中增删、排序或启停模块。
- 通过结果只表示当前数据支持相应规则通过，不代表已提交交易、实时账号操作一定成功或未来保证成交。
- 自动调价只做决策解释，覆盖评估时间、当前价、建议价、价差、原始成本底线和数据不可用等原因；不提供专属参数试改，不创建或推进调价任务。
- 固定数据预演不发起网络请求；主动刷新只允许只读数据获取。预演与刷新都不得调用交易提交或移动确认流程。

### 检查记录与数据版本

- 在现有 SQLModel 数据库中增加独立检查记录，兼容 SQLite 与 PostgreSQL，采用增量初始化，不修改历史交易记录。
- 保存账号与商品标识、检查类型、评估时间、有效策略及模块版本、必要输入、各输入的采集时间与来源、步骤结果和结果摘要。
- 策略记录保存已解析的有效参数，不依赖后来可能变化的当前策略配置。后续修改策略或更新行情不得改写原检查的解释。
- 记录逐件检查中的通过、拒绝、等待和数据失败。不为未进入逐件检查的候选商品虚构记录；全局暂停、账号不可用等状态继续通过现有状态界面说明。
- 正式流程在前置规则拒绝后保持提前停止，不为了将来可能的预演额外拉取后续行情；对应步骤记录为未执行或输入缺失。
- 只保存计算和解释所需的业务字段，不序列化完整运行配置、登录凭据、令牌密钥、支付链接或无关网络响应。
- 刷新创建关联原记录的新数据版本，同时比较原参数与临时参数，不能把新数据补写成过去检查时已有的数据。
- 重启后可以读取有效期内的记录。无法支持的输入或版本不得静默返回通过；原来已保存的解释仍按记录展示。
- 保留最近 7 天、最多 10,000 条检查记录，任一限制达到后清理最旧记录及其关联预演数据，不保留无限增长的孤立数据版本。
- 检查记录写入失败不改变正式交易判断，报告记录不可用；清理不得删除购买、成交或交易流水。

### 公开接口与参数保存

- 新增受现有 API 鉴权保护的检查记录列表、详情和主动刷新接口；列表支持分页及检查类型、名称、结果筛选。
- 扩展现有模拟接口，要求指定检查记录和临时参数，返回原参数与临时参数的比较结果及明确的数据版本。
- 无检查记录的旧模拟请求返回“请选择检查记录”等明确提示，不再返回固定示例通过结果。
- 不能找到或已经清理的记录返回明确不可用结果，不回退到示例数据。
- 主动刷新使用后台只读任务，复用现有账号校验与限流，不并发重复刷新同一记录。账号已切换或原账号不可用时不能静默改用另一个账号。
- 刷新失败时保留原记录和原结果，并显示数据获取失败的原因。
- 另存副本复用现有策略验证，生成新的自定义策略标识，不覆盖原策略，也不修改任何已启用策略标识。用户之后通过现有策略中心决定启用。

### 界面与行情展示

- 沿用 FastAPI 和原生 JavaScript，使用现有界面结构与视觉规范，不引入新的前端框架。
- 策略中心的原示例模拟入口替换为“检查记录与预演”；保留所有已有策略，不另保留示例演示入口。
- 列表显示检查时间、商品、类型、策略和结果摘要；详情提供原始解释、参数对照、差异结果及必要行情。
- 结果明确区分通过、拒绝、等待、数据不可用、不支持、未执行和未启用，不把这些状态合并为简单通过／失败。
- 图表展示已有历史数据的价格和成交量，注明来源、时间范围、币种与数据缺口。图表和规则计算使用同一数据版本；不为作图补造数据或修改计算依据。
- 原记录、刷新版本与临时参数比较在界面中明确区分。刷新是显式操作，连续调整参数不会触发自动行情更新。
- 记录为空时显示明确空状态；记录中没有历史行情时说明缺失原因，提供符合范围的主动刷新入口。
- 桌面和手机都能完成筛选、查看原因、比较参数和另存副本。

## Testing Decisions

测试边界沿用使用者已经批准的计划，不重新发起技术选型访谈。以公开功能接口和真实用户操作为主，验证业务行为，不测试内部函数命名、私有调用次数或某种固定代码组织方式。

### 主要测试边界

1. **功能接口集成测试**：通过正式检查流程产生记录，通过公开记录、预演、刷新和策略保存接口观察结果。使用隔离数据库和模拟平台响应，覆盖保存、读取、比较、清理、刷新失败、账号变化和重启读取。
2. **规则一致性与无交易副作用测试**：同一份输入、有效参数和评估时刻，正式流程与预演必须给出一致判断。隔离环境禁止真实网络，并在外部交易提交边界设置禁止调用的替身，以验证没有订单、付款、报价、撤单、上架、移动确认或调价任务副作用。
3. **浏览器行为测试**：加载真实页面及应用脚本，使用隔离 API 数据，验证用户能看到正确的原因、状态、数据时间、参数差异和图表，完成刷新及保存副本；覆盖桌面和手机视口。

### 必须覆盖的验收场景

- 成本率为 74% 的数据，上限 70% 时该项拒绝，上限改成 75% 时该项通过；后续检查仍独立执行，不能提前宣布整体通过。
- 原检查在成本率阶段拒绝且未获取历史数据；放宽参数后后续步骤显示无法判断，不伪造历史稳定性通过。
- 主动刷新得到新的完整数据后，两套参数均使用新版本和对应评估时刻重新计算；原记录仍可查看。
- 重复预演固定输入时，结果不受实际时钟流逝、当前行情或后来编辑正式策略的影响。
- 买入通过、规则拒绝、数据获取失败，普通上架暂缓与建议定价均有可解释结果；自动调价解释未到期、价差不足、底线限制和数据不可用。
- 未启用、未执行、缺数据和规则拒绝在接口及界面可区分。
- 声明式模块与内置模块遵守同样的数据版本和参数依据；不支持情况明确报告。
- 固定数据预演不产生网络调用；刷新只读、遵守限流、不重复启动同一记录的刷新，并且失败时保留旧结果。
- 对调价记录请求参数试改不得创建或推进调价任务，也不得更改正式调价设置。
- 另存副本产生新策略，原策略及其启用状态保持不变；未保存的临时参数不写回正式配置。
- 记录中不出现凭据、密钥、支付链接等敏感字段；账号切换不会让刷新使用错误上下文。
- 重启后保留期内记录可读；超过时间或数量限制后清理最旧检查记录及关联数据，但交易流水完整保留。
- 记录写入失败不改变正式策略判断；过期、已清理、版本不支持和无记录状态均有明确反馈。
- 图表的数据版本、币种和时间范围与判断一致；缺失数据不补造；手机页面能阅读比较结果并完成操作。
- 原示例模拟入口被替换；旧的无记录请求不能再产生示例通过结果；已有策略仍可正常查看和使用。

### 测试先例与回归

仓库已有临时 SQLite 的交易生命周期集成测试、模拟平台响应的分页与账号保护测试、真实页面配合隔离响应的浏览器测试，可沿用其隔离方法。

外部平台响应可以用固定输入替换，但应尽量保留真实规则计算、持久化和接口序列化路径。预期结果使用可独立核对的案例，不能在测试中复制实现算法作为断言。

每个功能切片先得到针对该行为的失败测试，再实现并验证；最后运行相关数据库与浏览器测试、完整回归和 JavaScript 语法检查。所有验证均不得挂载真实交易账户的凭据或对真实交易账户发起操作。

## Out of Scope

- 手动搜索任意饰品作为独立预演入口。
- 历史回测、模拟成交收益或未来收益预测。
- 独立的大盘研究看板、跨商品研究平台和高级图表工具。
- 自动调价专属参数的试改、保存和自动启用。
- 在预演中增删、排序或启停策略模块。
- 在预演或刷新中提交任何真实交易或创建调价任务。
- 自动覆盖、保存或启用正在使用的策略。
- 从不完整的旧日志补造完整检查记录。
- 为获得全量预演输入而改变正式扫描已有的提前停止行为。
- 更换前端框架、重新设计整个应用，或改变现有选品与定价算法。
- 自动部署或启动真实交易任务。

## Further Notes

- 使用者已通过交互式选项确认固定数据与主动刷新、真实记录入口、缺数据按需补取、简单走势图、另存未启用副本、7 天与 10,000 条保留限制、自动调价仅解释、替换旧示例模拟入口。
- 产品术语使用“策略预演”和“决策解释”。策略预演不称为回测，也不代表真实成交模拟。
- 本 spec 是第一版实现与验收的依据，状态为 ready-for-agent，无需额外 triage。需要分拆实现任务时，任务应引用本 spec 并保持相同业务边界。
- 建议实现顺序：共用规则和一致性验证；真实检查记录；公开预演与刷新功能；界面、图表和浏览器验收；完整回归。
- 实现、Git 提交、远端推送与部署是不同动作，应分别报告结果。本次发布 spec 不意味着业务功能已经实现或部署。
